## 1. 项目定位与介绍

### 1.1 面试官应该记住什么

项目是一套面向个人知识与任务处理的 AI 应用。核心价值是把模型调用放进有工具权限、上下文预算、持久状态、证据来源和执行记录的系统中。

对五年前端开发者，重点不是证明自己会调用一个聊天接口，而是证明：能够设计复杂交互与协议，理解模型的不确定性，承担应用端到端的设计、实现、验证和排障。

| 岗位 | 优先讲解顺序 | 必须准备的证据 |
|---|---|---|
| AI 应用 / Agent 工程 | Runtime → 工具调用 → RAG → 记忆 → Eval | 真实任务结果、失败 Trace、质量/成本/延迟对比 |
| 前端 / AI 全栈 | 用户操作链路 → 事件协议 → Runtime → 数据与可靠性 | 流式交互、确认续执行、取消、异常状态、模块契约 |

### 1.2 30 秒介绍

> 我有五年前端经验，现在向 AI 应用和全栈方向发展。我开发了一个个人知识助手，支持流式聊天、知识检索、长期记忆和工具执行。重点做了 Agent 的执行控制、上下文预算、工具确认、记忆原子写入和检索证据追踪，也通过 Trace 和测试定位执行中的问题。

“我开发了”应按实际责任范围改成“我负责了”。AI 辅助开发可以如实说明，但每个写进简历的设计都应能解释、修改和验证。

### 1.3 两分钟介绍

> 这个项目解决两个问题：一是个人知识分散在笔记和文档里，二是普通聊天应用无法可靠完成需要工具的任务。
>
> 应用以 Next.js 为 Web 和 API 入口，React 与 TypeScript 实现交互，Supabase 保存持久业务数据并提供向量检索，Redis 承担缓存和部分执行状态。聊天入口通过应用用例编排，模型与工具由自研 Runtime 连接。
>
> Runtime 的重点是控制执行：每轮检查上下文和消耗预算，处理模型提出的工具调用，限制重复调用和迭代次数，并支持取消、确认与计划执行。工具结果回灌模型后继续推进任务。
>
> 知识问答采用向量和关键词混合检索，配合查询改写、融合、重排和多样性选择，保留证据来源用于引用与追踪。长期记忆则独立管理用户事实，写入需要用户原文依据，事实与语义索引通过数据库事务维护一致性。
>
> 我可以从前端事件到服务端 Trace 复盘一次运行。目前确定性逻辑有回归测试；真实模型的任务成功率、检索收益和端到端延迟还需要用固定数据集持续验证。

### 1.4 当前技术边界

- 这是分层的 Next.js 应用，核心执行仍有大量逻辑位于 `lib`，不是已经完全解耦的微服务系统。
- 应用模型调用主要走 OpenAI-compatible 适配；内部使用 Anthropic 风格消息类型，不等于直接支持全部 Anthropic Provider 能力。
- Skill 使用 E2B 托管沙箱。可以讲接入、权限、生命周期与 Bundle 执行，不应声称自研了底层沙箱。
- 回答引用校验是规则观测，不能证明语义蕴含或事实真值。
- 多模态文档 RAG 为首版实现，真实环境启用与验收状态需单独核实。

## 2. 一条请求如何贯穿四个核心模块

### 2.1 建议讲解案例

用户提出：

> 结合我之前保存的 Agent 笔记，按照我偏好的简洁风格，总结工具调用的风险，并创建一个学习待办。

这是解释模块协作的示例，是否生成执行计划由当前执行策略决定，不应预先断言一定进入 plan 模式。创建待办是否弹出确认，应以该工具当前策略为准，不能把所有写操作等同于强制确认。

### 2.2 请求链路

```text
浏览器 ChatSession 发送任务
  → POST /api/chat 认证并取得会话租约
  → runChatUseCase 解析请求、恢复历史、解析用户配置
  → 构建 RetrievalPlan、召回记忆、组装 Prompt 与工具集合
  → 选择 direct / plan 执行策略
  → Runtime 请求模型
  → 模型返回文本或结构化工具调用
  → Runtime 检查权限、依赖、预算与重复调用
  → 工具执行：search_notes / 创建待办等
  → tool_result 回灌模型；必要时暂停等待确认或补充信息
  → 模型继续生成
  → 记录引用检查、Trace、Usage 与上下文快照
  → SSE 事件驱动界面更新
  → 满足写入条件时触发异步记忆沉淀
```

这是一张逻辑关系图，不意味着所有步骤始终执行，也不意味着每个准备阶段都有并行优化。

### 2.3 四个模块分别回答什么

| 模块 | 回答的问题 | 不应承担的职责 |
|---|---|---|
| Runtime | 下一步能否执行、如何继续、何时停止 | 判断一切业务目标已经达成 |
| 工具调用 | 如何把结构化动作转为受控操作和结果 | 把模型参数视为用户授权 |
| 记忆 | 用户曾明确表达什么、当前什么事实有效 | 把模型推测永久当作用户事实 |
| RAG | 当前任务有哪些可追溯的知识材料 | 把相似度高视为结论一定正确 |

## 3. Runtime：控制模型的执行过程

源码入口：[runtime/index.ts](../../lib/agent/runtime/index.ts)、[run-chat.ts](../../packages/application/src/chat/run-chat.ts)。

### 3.1 定义与职责

Runtime 是控制模型、工具、消息状态和执行终态的程序。模型负责生成文本与动作建议；Runtime 管理这些建议能否执行、结果如何回到下一轮，以及执行是否继续。

Agent Loop 是 Runtime 的一部分。上下文准备、计划选择、确认恢复、持久化和观测还涉及应用层及其他模块，不能把整个系统缩成一个 `while` 循环。

### 3.2 主循环伪代码

下面用于面试讲解，省略实际实现中的事件与观测逻辑，不是可以直接替换源码的程序。

```ts
while (withinIterationLimit) {
  checkCancellation();
  prepareAndCompactContext();
  checkRequestWindowAndRunBudget();

  const response = await callModel(messages, allowedTools);
  accountModelUsage(response.usage);

  if (response.outputLimitReached) return stop("max_tokens");
  if (!response.toolCalls.length) return completeWithTrace(response);

  const candidates = checkDependenciesAndCallBudgets(response.toolCalls);
  checkRepeatedCalls(candidates);
  const results = await executeWithPolicies(candidates);
  appendPairedToolMessages(messages, response, results);

  if (needsUserInput(results)) return checkpointAndPause(results);
}
return stop("max_iterations");
```

注意：伪代码中的先后关系概括多个实现阶段；“有终态”不等于“语义上完成任务”。

### 3.3 两类预算

| 预算 | 解决的问题 | 计算依据 |
|---|---|---|
| 单次上下文窗口 | 本轮请求是否放得进模型 | system、历史消息、工具 Schema、图片估算、输出预留 |
| Loop 累计 Token 消耗 | 本次执行是否持续花费过多 | 模型返回 usage，缺失时回退本地估算 |

单次窗口可用输入容量的讲解公式：

```text
可用输入预算 = 模型窗口 - 输出预留 - 安全余量
输入估算 = system + messages + tool schemas + media
```

窗口是每次请求约束；累计预算需要把各轮消耗相加。一个任务每轮仅使用少量上下文，仍可能因不断调用工具而耗尽累计预算。

当前 `limits.ts` 中 Loop 默认累计预算为 128,000 Token，默认输出预留常量为 4,096，压缩窗口上限为 80,000。实际 Loop 会通过 `getModelMaxOutputTokens(model)` 获取所选模型的输出预留，不能把 4,096 当作每次请求固定值。Runtime 中常规压缩触发/目标比例为 0.6/0.3。这些是当前配置值，不是所有模型通用的最佳参数。

特别注意：Loop Token 预算不能宣称覆盖系统所有付费调用。策略选择、记忆提取、Embedding、重排与视觉分析等费用应分别核对统计及预算路径。

### 3.4 上下文压缩为什么不是删除前半段

工具消息有协议关联：assistant 的 `tool_use.id` 对应后续 `tool_result.tool_use_id`。如果只保留调用或只保留结果，可能造成 Provider 拒绝请求或模型误解执行状态。

当前压缩逻辑考虑工具调用/结果配对边界，保留起始与近期消息，对中间历史生成摘要。可使用语义压缩，并在不适用或失败时采用确定性摘要。

摘要应保留：用户目标、约束、已完成工作、失败状态、未解决问题、关键文件和产物引用。图片原始内容不应无限跟随历史，应保留定位信息并按需重新读取。

压缩是有损的。即使摘要格式正确，也可能丢失数值、否定或用户约束；需要多轮任务回归测试，不能靠“摘要更短”判断成功。

### 3.5 Prompt Pipe 与 ContextPlan

当前 Prompt Pipe 已有段排序、预算裁剪和裁剪决策记录，不再只是裸字符串拼接。

`PromptSegment` 描述来源、信任等级、优先级及内容；`buildPromptPipe` 负责保留或省略；`ContextPlan` 记录历史来源、各来源 Token、内容哈希与决策。稳定段优先排列有利于稳定请求前缀，但不保证 Provider 缓存一定命中。

面试讲法：

> 我把“本轮模型看到了什么”作为可审计的执行输入。出现错误时，可以判断是没召回、被裁剪、压缩丢失，还是模型已经看到正确材料但没有遵循。

### 3.6 direct、plan 与审核

当前执行策略区分：

- `direct`：普通问答、单个交付目标或短工具链。
- `plan`：多个交付目标、跨阶段依赖、检查点与恢复需求。
- `requiresPlanReview`：用户明确要求先看计划并等待确认。

**生成计划、审核计划、批准具体工具是不同维度。** 复杂任务可以进入 plan，但不一定要人工审核；用户审核了计划，也不代表所有副作用工具获得授权。

策略结果会经过结构校验。策略判断超时、输出无效或 Provider 出错时，当前实现采用仅回答/澄清、不调用工具的降级方式，避免无约束继续执行。

### 3.7 终态与取消

重要终态包括完成、输出上限、预算耗尽、重复工具调用、迭代上限、等待确认、等待用户输入，以及请求取消等。具体事件与 Trace 终态由各执行路径维护。

取消从浏览器的 AbortController 传到请求、模型调用和工具上下文。工具超时包装器会发出 abort 并结束等待。

但取消是否真正停止工作，取决于底层 SDK、工具和外部系统是否响应 signal。外部写操作已经发生时，取消不等于撤销，必须报告真实状态。

### 3.8 Runtime 高频追问

#### Q1：为什么没有直接全部交给 SDK 的 Agent 功能？

SDK 很适合模型调用与协议适配。项目需要把确认、快照、证据、前端事件、预算和 Trace 接入同一执行链，因此保留自研编排。代价是要自己维护协议兼容、状态正确性和测试。应讲具体需求，不要声称自研天然优于框架。

#### Q2：如何防止无限循环？

同时限制迭代次数、累计 Token、检索调用次数，并检测重复工具签名。每一层处理不同失控方式；仅限制轮数无法控制单次巨量结果，仅限制 Token 也无法阻止重复副作用。

#### Q3：重复检测和业务幂等有什么区别？

重复检测主要减少当前执行中的重复调用。业务幂等需要跨请求、跨重试和跨实例识别同一个动作，例如数据库唯一约束或下游 idempotency key；Runtime 的签名去重不能替代它。

#### Q4：模型不返回 usage 怎么办？

预算记账回退本地估算，并明确它是估算。真实计费仍应以 Provider 口径为准。不能把图片固定 Token 估算或消息 JSON Token 数当作准确账单。

#### Q5：Loop completed 是否代表任务成功？

不是。模型可能自然结束但漏掉交付项。需要按任务定义验收，例如待办是否真的写入、报告是否有必要字段、答案是否覆盖关键问题。当前完成终态不构成通用语义验收。

#### Q6：多轮压缩如何验证？

构造长任务，埋入目标、否定条件、数值和工具结果，触发一次或多次压缩后检查是否仍遵守。还要验证所有 tool_use/tool_result 配对合法。分别测协议正确性和任务信息保真。

#### Q7：会话并发如何处理？

聊天入口有按用户与会话的 Redis 租约，运行时续期，失去租约时取消；确认恢复还校验快照版本。它们降低同一会话的并发覆盖风险，不能被描述成所有持久化操作都已事务化。

#### Q8：Runtime 下一步怎么改？

先把大文件中的执行状态、工具调度和结果整形进一步分离；为异步持久化加入可靠 worker；增加任务级验收。是否引入 DAG 或独立服务应由实际任务与扩缩容需求决定。

## 4. 工具调用：从模型建议到真实动作

源码入口：[types.ts](../../lib/agent/tools/types.ts)、[registry.ts](../../lib/agent/tools/registry.ts)、[tool-router.ts](../../lib/agent/tools/tool-router.ts)。

### 4.1 完整链路

```text
工具定义与注册
  → 按用户配置、模型能力、检索计划和任务意图选择工具
  → 投影为模型可见 name / description / input_schema
  → Provider 返回 tool call
  → Runtime 检查本轮工具范围、调用预算、能力依赖和重复调用
  → Router 处理确认、危险操作拒绝、限流与超时
  → 具体工具检查参数、身份与资源所有权后执行
  → 结果整形、保存大结果、生成 Trace 与 UI 事件
  → 按 tool call ID 写回 tool_result
```

“工具暴露给模型”只是可选动作范围；真正执行还需服务端检查。不能以隐藏按钮或 Prompt 中说“不要调用”为权限控制。

### 4.2 工具契约

| 字段 | 作用 | 面试注意 |
|---|---|---|
| name / description / input_schema | 模型选择工具和生成参数 | 描述也是影响效果的输入，需要回归 |
| capabilities | 用稳定能力标签表达工具能做什么 | 降低依赖具体工具名的耦合 |
| riskLevel | safe / confirm / dangerous | safe 不代表无成本、无错误或已验证所有权 |
| runtime | 超时、限流、副作用、并发等策略 | 字段声明不等于所有资源限制都已执行 |
| outputPolicy | 结果作为事实、证据、回执或流程信号 | 决定验证与引用语义 |
| execute | 实际业务执行 | 必须再次检查参数和资源边界 |

Registry 通过 Map 注册，拒绝重名，并投影模型 Schema。内部风险策略和执行函数不会发送给模型。

### 4.3 四类输出语义

| grounding 类型 | 例子 | 能证明什么 |
|---|---|---|
| authoritative_result | 时间、计算结果 | 当前调用条件下的确定性计算/读取结果 |
| cited_evidence | 知识检索、网页材料 | 存在这些来源材料，答案应保留对应引用 |
| action_receipt | 创建待办、运行 Skill | 动作状态与返回产物；不证明任意事实结论 |
| none | ask_user、未建立证据契约的外部读取 | 流程信息或普通工具内容 |

即使执行接口可靠，输入、时区、数据源或程序本身仍可能有问题；authoritative_result 不是绝对真值。

### 4.4 参数校验与权限

项目的参数校验分散在具体工具与适配器中。MCP 使用 AJV 校验远端工具参数；内置工具有各自解析与校验逻辑。通用 Router 不应被描述成统一对所有工具运行完整 JSON Schema 校验。

模型 Schema 主要指导生成，不能替代运行时校验。用户身份应来自服务端认证上下文，不能接受模型参数里的 userId 作为可信身份；查询还需验证资源所有权。

`requiresAuth` 等策略字段不意味着 Router 自动落实全部认证要求。面试时应指向入口认证、工具内检查和数据库过滤的具体代码。

### 4.5 并发与依赖

当前调度器将高风险、需要确认及 `write` 工具放入串行集合；其他符合条件的工具按 concurrencyGroup 分组，在组内按最大并发分批执行。

需要准确说明：当前不同并发组是依次处理，且并行集合先于串行集合执行。返回结果按原调用顺序还原，但**返回顺序不等于真实执行顺序**。不能声称它是任意依赖 DAG 调度器，也不能把“external”字段本身当作自动串行保证。

对严格依赖，应该拆成不同模型轮次/计划步骤或使用明确能力前置检查，而不是依赖模型在同一批中的排列。

### 4.6 确认与续执行

确认不是发送一个 `approved: true` 就结束。当前服务端保存加密 checkpoint，恢复时检查：

1. token 属于当前用户，且记录仍有效。
2. 会话匹配，callId 在待确认列表。
3. 工具/配置指纹仍匹配。
4. 原模型可解析，客户端不能随意替换。
5. 上下文快照版本没有被后续对话更新。
6. 原子 claim 确认记录，避免并发重复执行；已经保存的响应可以重放。

Redis claim 将 busy 标记与加密状态放在同一 key，避免只丢锁却保留可重放状态。若副作用执行后崩溃、状态未保存，系统可能保留“结果未知”，要求核实，而不是盲目再次执行。

这降低重复风险，但不能宣称所有下游写操作具备 exactly-once 语义。

### 4.7 超时、限流与大结果

- 超时使用 AbortController 与 Promise.race；工具应响应 signal，否则底层工作可能继续。
- 通用限流当前是进程内 Map 的一分钟窗口，多实例无法共享全局计数。需要全局配额时应迁移到 Redis 或持久限流服务。
- 大结果可截断并保存到 artifact，模型先看到摘要与 artifactId，需要时通过工具取回。
- artifact 当前包含本地存储路径，跨实例读取需要对象存储或共享存储方案。
- `memoryLimitMb`、`sandboxed` 等字段不能直接证明内置工具被 OS 级隔离；E2B 执行和普通进程内工具应分别讨论。

### 4.8 MCP 与 Skill 怎么讲

MCP 接入外部服务的工具发现与调用，项目通过适配器将它们统一为 ToolDefinition。工具准入和确认策略由本地配置决定，不能仅相信远端“只读”提示。请求级连接会在结束、异常或取消时清理。

Skill 是可执行能力及其说明、Bundle 和运行约束，项目使用 E2B 执行不可信代码。MCP 工具调用不意味着代码进入 E2B；二者只是能被同一 Runtime 编排。

深挖材料见 [MCP / Skill 面试指南](./mcp-skill-interview-guide.md)。

### 4.9 工具调用高频追问

#### Q1：Function Calling、工具执行和 MCP 有什么区别？

Function Calling 是模型输出结构化动作的机制；工具执行是应用把动作转为实际操作；MCP 是外部能力发现与通信协议。模型发出调用不等于操作已经执行，MCP 也不替应用完成授权。

#### Q2：模型编造工具名怎么办？

只执行本轮允许范围内的注册工具；未知工具返回结构化错误。不能退化成把名字交给 eval、shell 或动态 import。

#### Q3：参数符合 Schema，为什么仍可能越权？

Schema 可以证明参数形状，却不能证明用户拥有某个文件或待办。格式验证、认证、资源授权是三件事，必须分别执行。

#### Q4：批准计划能否批准写操作？

不能自动推导。计划批准表达对任务步骤的认可，具体动作仍受工具策略与确认 checkpoint 约束，尤其是参数和服务配置发生变化时。

#### Q5：失败后哪些工具可以重试？

只读调用通常较适合有限重试，仍需考虑成本与限流；写操作只有在有幂等键或能核实结果时才适合重试。连接超时可能发生在远端已经执行之后，应保留状态未知。

#### Q6：如何测试工具路由？

测试工具选择、参数、风险拒绝、确认恢复、超时与重复调用；同时检查失败工具是否产生副作用，以及模型是否正确收到失败结果。单独测 execute 成功不够。

#### Q7：新增一个工具要改哪里？

实现 ToolDefinition，声明能力、输出语义与运行策略，注册后补参数、权限和执行测试；再验证路由是否可见、Prompt 是否正确引导、Trace/UI 是否可展示。元数据减少中央硬编码，但现有代码仍有工具特例，不能声称完全零改动。

#### Q8：外部网页中的指令为什么危险？

外部内容可能诱导模型调用具有副作用的工具。应把网页/工具内容标为数据，保持本地授权，限制工具集合并测试注入场景。Prompt 提醒不能构成隔离证明。

## 5. 记忆：事实写入、召回与生命周期

源码入口：[memory-flow.ts](../../lib/agent/memory/memory-flow.ts)、[atomic-writer.ts](../../lib/agent/memory/atomic-writer.ts)、[fusion.ts](../../lib/agent/memory/fusion.ts)。

### 5.1 为什么不能只保存聊天记录

历史记录按时间组织，稳定用户事实按意义组织。所有历史直接进入模型会增长成本、带入过期信息，也难以支持显式纠错与忘记。

| 数据 | 保存什么 | 典型用途 |
|---|---|---|
| 用户可见消息 | 用户与助手的对话记录 | 展示、审计、历史恢复 |
| 执行上下文快照 | 模型消息和工具执行上下文 | 继续任务，不等同于 UI 消息 |
| 会话缓存 | 当前会话的短期状态 | 降低恢复延迟 |
| 长期事实 | 稳定用户事实、偏好、项目信息 | 个性化与明确事实管理 |
| 语义索引 | 事实的向量与召回字段 | 根据问题定位相关记忆 |
| 历史版本 | 被替代/纠正事实及时间语义 | 解释过去记录与变化 |

长期事实与语义索引是同一事实的不同存储视角，不代表互不相关的两个事实来源。

### 5.2 召回链路

```text
解析用户记忆配置
  → 预取路径判断问题是否需要长期记忆
  → 语义与关键词宽召回
  → 按 key 合并候选并集
  → 状态、置信度等治理过滤
  → 规则排序 / 可选 Cross-Encoder 重排与准入
  → 严格过滤，选 Top-K
  → 注入 Prompt，记录候选和最终选择
```

模型主动调用的 `recall_memory` 与请求前预取共享主要召回管线，但触发机制不同。不能声称所有记忆访问都被同一个预取正则门控。

### 5.3 为什么要门控

“我偏好什么回答风格”需要个人记忆；“解释事件循环”通常不需要。每轮预取会增加延迟与成本，也可能把无关画像注入模型。

当前预取包含规则门控，优点是确定、易测；缺点是可能漏掉隐含个人上下文或多轮指代。改进应看误召回与漏召回数据，不是简单扩大规则覆盖。

### 5.4 混合召回的取舍

语义通道适合不同表达；关键词适合姓名、金额、缩写、稳定 key 等精确线索。两者融合取并集，避免某一路漏检把另一通道的候选删除。

当前有 `vector_only`、`weighted`、`rrf` 三种策略，默认 weighted 是待验证的选择。不要说已经证明它优于 RRF。

规则排序中的新近度使用事实的 updatedAt/createdAt，而不是 lastAccessedAt，避免“被召回一次 → 访问时间更新 → 更容易被召回”的自我强化。访问时间仍可记录，但不能误说它就是当前 recency 的依据。

宽召回先给足候选，最终准入再收紧。只降低向量入口阈值、仍保留同样的 Top-K 截断，可能对最终结果没有增益；必须查看新增候选是否真的进入后续选择。

可选重排也区分配置、是否实际调用、是否采用模型准入及失败降级。规则分数、余弦分数和 Cross-Encoder 分数不是天然可交换的尺度。

### 5.5 写入链路

```text
对话满足沉淀条件
  → 模型抽取候选事实和 evidenceExcerpt
  → 验证证据来自用户原文、过滤限制内容、规范化 key
  → 读取现有候选，判断新增/更新/重复/纠错/忘记
  → 生成 embedding
  → 数据库 RPC 原子写入长期事实与语义索引
  → 必要时归档旧版本并记录时间、来源与 requestId
```

可记忆示例：稳定岗位、长期偏好、持续项目背景。

不应默认记忆：一次性需求、模型推断的隐私、凭据、中间推理、未经用户原文支持的事实。

`evidenceExcerpt` 要求是用户消息中的连续原文，并经过限制内容过滤。但“原文存在”仍不等于抽取结论一定成立：否定、引用他人的话、假设语气都可能被误解，因此还需要写入负例评测。

### 5.6 原子双写

错误做法：

```ts
await Promise.all([
  writeLongTermFact(fact),
  writeSemanticIndex(fact),
]);
```

Promise.all 只控制等待，不能回滚已完成的数据库写入。一成一败会产生“主记录存在但召回不到”或“主记录失效但向量仍可召回”。

当前先生成 embedding，再调用数据库 RPC，让两张表在同一事务里更新。Embedding 失败不会启动该次数据库双写。注意：这保证的是该事务中的存储一致性，不能保证整个异步任务一定获得执行。

同库采用事务是当前简单方案；跨库或独立向量服务可使用主记录 + outbox + 可重建索引，此时需要接受并治理索引短暂滞后。

### 5.7 并发冲突

当前支持 expectedVersion。同一 key 被并发修改后，旧决策会收到版本冲突；consolidate 重新读取候选、重做决策，最多再尝试一次。

面试可用场景：两个请求同时把相同偏好沉淀到同一 key。第二个请求重读后可能发现内容已经存在，应转为 NOOP，而非覆盖或生成重复记录。

边界：只有取得目标当前行可信版本时才传 expectedVersion；某些由语义候选选择另一 key 的路径没有版本条件，依靠事务内行锁串行化。行锁并不能自动验证事务开始之前的语义决策仍正确。

### 5.8 演变、纠错与忘记

| 用户表达 | 语义 | 实现关注点 |
|---|---|---|
| 以前住北京，现在搬到上海 | evolution | 旧值曾有效，新值从变化时刻开始有效 |
| 之前说错了，我一直住上海 | correction | 旧值是错误事实，应改变其有效性语义 |
| 不再用这个偏好回答 | 软失效 | 从当前召回排除，保留治理/历史信息 |
| 彻底删除这条个人信息 | 硬删除 | 当前事实、语义索引及相关历史一起处理 |

项目有原子失效与 purge 能力，硬删除路径要求 userId。不能只删长期表而保留向量或历史，否则可能被再次召回。

忘记数据库记录不等于抹除所有旧聊天与 Trace。当前上下文、缓存、历史消息和数据保留策略也应检查；不要宣称已经完成全系统隐私擦除。

### 5.9 当前可靠性边界

聊天后的部分记忆沉淀仍是 `void` 异步调用。进程退出或运行环境结束可能导致任务未完成；catch 到错误不等于可靠交付。

合理演进：聊天阶段写入 durable event，worker 原子领取、有限重试、死信、按 requestId 幂等，并监控积压与成功率。这是建议方案，不能写成已经完成。

### 5.10 记忆高频追问

#### Q1：为什么记忆和 RAG 分开？

记忆保存系统从用户表达中提取的个人事实，可能抽错，需要纠错与忘记；RAG 保存用户整理的笔记或外部文档，需要来源与版本。二者生命周期、信任程度和用户预期不同。

#### Q2：有 userId 字段是否就隔离了？

不是。必须检查数据库查询、RPC、缓存 key、历史查询和删除路径是否真的使用身份条件。Service Role 绕过 RLS，应用漏条件仍会越权。用两个用户的交叉访问测试证明。

#### Q3：记忆越多是否越好？

不是。错误或无关记忆会污染回答。应该优先写入 precision，召回时看相关性、状态与时间，并限制注入预算；不是无限扩大召回量。

#### Q4：同一事实不同说法如何去重？

使用稳定 key 与候选检索辅助判定新增/更新/重复。稳定 key 约束降低漂移，但语义判定仍可能错，需测试别名、否定、近似主题和不同业务范围。

#### Q5：为什么事务有了还要版本校验？

事务保证写入原子性；版本校验防止基于旧事实作出的决策覆盖新事实。二者解决不同问题。只在写入时加锁，不代表模型此前的判定仍然有效。

#### Q6：如何评测记忆？

分写入和召回两组。写入测该记/不该记、证据支持、重复、更新、纠错、忘记；召回测门控 precision/recall、Top-K 命中、无关注入与过期记忆。另加跨用户与并发测试。

#### Q7：记忆重排失败怎么办？

当前可回退规则准入与排序，并保留是否调用、错误与降级原因。业务上应优先不注入错误信息，不能因一个重排服务失败而放开所有候选。

#### Q8：为什么不能把助手自己的答案再写成事实？

模型可能猜测或复述错误信息，反复沉淀会形成自我强化。写入需要用户原文依据；即便引用了用户原文，也仍需判断是否真正支持候选事实。

## 6. RAG：从知识入库到证据回答

源码入口：[retriever.ts](../../lib/knowledge/retriever.ts)、[search-notes.ts](../../lib/agent/tools/search-notes.ts)、[retrieval-router.ts](../../lib/agent/rag/retrieval-router.ts)。

### 6.1 离线与在线是两条链路

```text
入库：Notion / 文件 → 解析与规范化 → 切块 → Embedding
    → 同库原子发布索引与元数据 → 更新版本/画像

查询：用户问题与历史 → RetrievalPlan → 独立查询与改写
    → 向量 + 关键词召回 → 融合 → 重排 → MMR
    → 证据评分与有限尝试 → 上下文组装
    → 模型回答 → 引用检查与 Trace
```

文档中的“在线”指查询阶段，不代表本次已检查线上服务。

### 6.2 数据解析、切块与原子发布

切块应保留标题路径、段落结构、来源与必要的位置字段，并受 Token 长度限制。不能只按照固定字符数任意切割：中文 Token 比例、代码块、表格和段落边界都不同。

小 chunk 更容易匹配具体问题，但缺上下文；大 chunk 保留语义，却可能降低向量辨识度并占用预算。Parent-Child 思路是用小块检索，再补充有限父上下文。

Embedding 入库还需检查维度、数值合法性与模型配置。换模型时，即使维度相同也不能假定向量空间兼容，需要重建/版本隔离。

知识摄取已有数据库任务领取、lease、续期、有限重试和 dead 状态。索引发布使用事务/RPC 与版本校验，文件和视觉链路还有 generation、文件校验与租约校验，降低删除/重建竞态。

数据库索引原子提交不等于 Storage 文件与数据库获得跨系统事务；对象残留仍需要清理机制。

### 6.3 RetrievalPlan 不等于 ExecutionPlan

| 计划 | 决定什么 |
|---|---|
| RetrievalPlan | 是否检索、knowledge/web/both/no_retrieval、查询、过滤、尝试预算与证据要求 |
| ExecutionPlan | 交付阶段、步骤顺序、允许工具与恢复位置 |

联网开关是用户允许使用 Web 的边界；检索 route 表达任务的数据源需求/优先级，不能把联网关闭覆盖掉。工具集合最终还要与模型能力、配置和执行步骤约束求交。

路由可能使用规则或配置后的模型辅助判断，需从 routeDecision 看实际路径。不要把模型路由描述成所有请求必经的统一实现。

### 6.4 查询改写与多查询

独立问题改写解决指代，例如“它和上面那个有什么区别”需要恢复具体对象。多查询拓展可能覆盖缩写、同义表达或不同子问题。

风险是改写改变用户限制、扩大检索范围、引入额外成本。应保留原查询，记录改写与尝试原因，并测试是否错误改变否定、时间和实体条件。

多查询不是多跳推理。多个表达问同一个问题，与分别检索多个实体并完成关系推理，是不同需求。

### 6.5 向量、关键词与融合

向量擅长语义近似，关键词擅长精确实体与词项。两路分数的尺度不同，直接相加往往没有合理含义。

RRF 的基础公式：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

加权 RRF 可以为各路增加权重。它只依赖排名，易于组合异构检索结果，但丢失原始分数差距；多查询数量与权重也会影响排序。

校准加权融合则保留部分原始分与排名信息，需要用数据调权重。当前支持 RRF 与 weighted，不能仅凭公式证明谁更好。

### 6.6 重排与 MMR

Cross-Encoder 直接评估 query 与候选内容的相关性，适合较小候选集，代价是额外延迟、成本和服务依赖。当前可以按配置及条件启用，不是默认保证每次调用。

MMR 的概念公式：

```text
候选价值 = λ × 与问题的相关性
         - (1 - λ) × 与已选内容的最大相似性
```

它减少相似 chunk 占满上下文。过度追求多样性也可能删除同主题必需细节，因此 λ 与最终 Top-K 需要一起评测。

### 6.7 证据评分、有限重试与上下文

EvidenceGrade 记录相关性、覆盖和强弱等信号。`search_notes` 有有限尝试及多跳覆盖处理，但它不是无限自主研究器，也不是独立语义证明系统。

当候选达到最低相关性但整体不充分时，当前链路可能保留弱证据并提示保守引用。应该区分：检索为空、材料弱、材料充分，不能把它们都归成“检索成功”。

模型上下文组装还受 Token 预算影响。当前实现优先保留命中的子块，再补周边文本，避免前缀截断只留下父文档开头。评测时应检查最终送入模型的内容，不能只测原始检索列表。

### 6.8 EvidenceBundle 与回答检查

EvidenceItem 保存 evidenceId、文档/版本、正文、来源、信任标签、分数和引用定位；EvidenceBundle 保存本轮查询、索引版本、尝试与整体等级。

最终检查关注：

- citation coverage：事实句有没有可关联引用。
- citation precision：引用是否存在，并达到最低词面支持。
- groundedness：事实句能否获得已知证据的最低词面支持。

当前校验使用规则分句与词面重合，并允许符合条件的同节引用继承。它无法可靠识别否定、数值冲突、因果错误和复杂推理。

Runtime 当前记录检查报告，`guarded: false`，不因报告直接替换模型答案。**严禁把这一能力写成“事实校验通过后才输出”或“消除了幻觉”。**

如果未来加入语义 verifier，仍要测误判、延迟和成本；即便 verifier 是 LLM，也不能自动视为事实真值。

### 6.9 缓存与数据隔离

检索缓存 key 包含 tenantId、indexVersion、source、query、filters、threshold、limit 和 strategyVersion 等维度，避免跨用户复用和索引更新后继续使用旧结果。具体检索层还需确认 Provider/模型配置参与相关缓存版本。

当前缓存主要是进程内 TTL/LRU：能降低重复请求开销，但不保证多实例共享、跨重启保留或全局一致性。

查询数据库/RPC 也必须携带用户范围。Private content 作为信任标签描述来源，不意味着内容里的指令有权修改系统策略。

### 6.10 多模态文档 RAG：加分项与边界

首版路线是“文字代理检索 + 按需读原图”：

1. PDF 页或 DOCX 图片登记资源。
2. 视觉模型生成文字转写与图形描述，作为额外 chunk 检索。
3. 检索返回资源 ID，并在本轮建立访问授权。
4. `read_knowledge_visual` 读取原图或获得视觉观察。
5. 主模型获得图像或文字观察，答案保留出处。

访问限定 userId、requestId、资源版本等；单次最多读取 3 个不同资源，单轮最多两次读取、最多 6 张。图片字节在模型请求前加载，不应把新增 base64 无限写入历史和 telemetry。

视觉代理可能误读；图中实体未被描述就可能召回不到；仅加载图片不构成文字事实支持。当前无多模态 embedding、独立 OCR、区域裁剪或完整表格结构化能力。真实视觉模型、迁移和端到端质量仍需验收。

详细状态见 [图文混合 RAG 实现](../rag/multimodal-document-rag-implementation.md)。

### 6.11 RAG 高频追问

#### Q1：为什么不用更大上下文直接塞全部笔记？

数据增长后成本和延迟上升，且无关内容可能干扰模型。检索帮助控制输入规模与来源；小知识集合可以直接提供全文作为基线，不能预设 RAG 永远更好。

#### Q2：为什么不直接微调？

知识经常更新，且需要可删除、可追踪来源，检索更便于维护。微调主要改变行为或特定能力，不应被当作可审计文档数据库；二者也可以组合。

#### Q3：Top-K 越大越好吗？

召回率可能上升，但噪声、冗余和 Token 也上升。需联合评估候选池、重排、最终上下文、答案质量和成本，不能只看 Recall@K。

#### Q4：向量相似度高为什么仍答错？

相似可能只是主题相同，材料可能过期、相反或不完整。还可能在上下文裁剪中丢失关键内容，或模型错误解读。沿 Trace 分阶段定位，不要先改 Prompt。

#### Q5：关键词是否就是 BM25？

不能直接等同。项目有 PostgreSQL 关键词/词项召回与应用层处理，具体算法以 SQL 和 lexical 实现为准；使用关键词检索不代表已部署 BM25 搜索引擎。

#### Q6：什么地方体现 Agentic RAG？

有数据源计划、工具化检索、证据评分和有限尝试，检索过程参与 Agent 执行。范围是受控的查询编排，不是无限自主探索或已经证明的多跳推理能力。

#### Q7：怎样证明混合检索与重排有效？

固定数据集与索引，比较 vector-only、hybrid、hybrid+rerank 等方案，记录 Recall/MRR/nDCG、最终上下文命中、答案评分、延迟和成本。对失败样本看 Trace，避免只展示几个成功例子。

#### Q8：更新或删除文档时如何避免旧结果？

使用索引版本、原子发布与任务租约，相关资源读取再校验版本；缓存 key 随版本变化。仍需真实数据库的并发测试及 Storage 清理验证，不能只依赖 mock。

#### Q9：引用存在为什么不能证明答案正确？

引用只证明有这个来源。证据可能写“收入没有增长”，答案却写“收入增长”，词面重合仍高。需要更强的语义检查和人工标注，当前规则报告应明确局限。

#### Q10：检索最先优化哪一阶段？

先分解错误：未入库、没召回、排序低、上下文丢失、模型误读。根据错误占比选优化点。召回不到时加回答 Prompt 通常无效，已召回正确材料时盲目扩大候选也未必有用。

## 7. 四个模块的协作与边界

### 7.1 三个最容易混淆的概念

| 概念对 | 区别 |
|---|---|
| memory vs context compaction | 前者管理跨轮稳定事实，后者压缩当前任务历史 |
| tool result vs evidence | 前者是执行返回；只有建立证据语义与来源后才能按证据治理 |
| completed vs success | 前者是执行终态；后者要按业务目标验收 |

### 7.2 综合故障诊断

| 症状 | 优先检查 | 不应直接推断 |
|---|---|---|
| 忘了用户偏好 | 配置、门控、候选、准入、Prompt 裁剪 | 模型一定不支持记忆 |
| 回答笔记问题却没检索 | route、工具可见性、策略降级、模型选择 | 向量库出故障 |
| 找到材料但答错 | 最终上下文、版本、证据含义、模型输出 | 必须换 Embedding |
| 写操作重复 | 确认记录、请求重试、下游幂等、执行未知 | Loop 去重足以解决 |
| 中止后仍产生结果 | signal 传递、SDK 支持、外部副作用 | 前端 Abort 就会回滚 |
| 多轮任务丢约束 | 快照来源、压缩摘要、预算裁剪 | 长期记忆应该记所有消息 |

### 7.3 面试官问“最难的部分是什么”

选自己真正理解的一件事，按下面结构回答：

> 最难的是让工具确认后继续执行仍保持状态一致。界面上的确认按钮很简单，但服务端要知道批准的是哪个调用、原参数与配置是否变化、会话是否有更新，以及重复点击能否再次产生副作用。我通过服务端 checkpoint、指纹和快照版本校验，以及原子领取与响应重放降低风险。外部动作成功后本地崩溃仍可能产生未知状态，所以不能宣称 exactly-once，需要下游幂等或结果核实。

其他可选题：记忆原子双写与版本冲突；工具消息配对压缩；检索命中与最终回答错误的分阶段定位。

## 8. 评测、可观测性与面试证据

### 8.1 测试分层

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 纯函数/规则测试 | 预算、配对、融合、分句等确定性行为 | 真实模型是否理解任务 |
| mock 编排测试 | 工具顺序、错误路径、暂停与恢复 | SDK、数据库和网络兼容性 |
| 数据库/Redis 集成测试 | RPC、租约、事务、隔离与竞态 | 真实生成质量 |
| live eval | 固定环境中的模型与检索行为 | 所有用户请求都同样表现 |
| 端到端验收 | UI 到模型和存储的完整链路 | 长期可用性和大规模性能 |

本次前置分析运行了架构检查和 8 个测试文件、51 条用例，通过。该记录只适用于执行时的工作区，不代表全文全部能力或生产已经验收。

### 8.2 每个模块建议指标

| 模块 | 指标 | 需要先定义什么 |
|---|---|---|
| Runtime | 任务成功率、终态分布、轮数、取消耗时、Token/任务 | 成功验收规则及统计对象 |
| 工具 | 正确选择率、参数通过率、执行错误率、确认重复率 | 应调用/不应调用的标签 |
| 记忆写入 | precision、误写、重复、更新/忘记正确率 | 用户表达是否支持候选事实 |
| 记忆召回 | 门控 P/R、Recall@K、无关注入率 | 每题相关记忆集合 |
| RAG | Recall@K、MRR/nDCG、上下文命中、答案正确率 | gold 文档/chunk 和答案依据 |
| 产品体验 | 首文本延迟、完成延迟、p95、错误恢复成功率 | 从哪个时间点计时、是否含策略调用 |

工具成功率不是任务成功率；词面 groundedness 不是答案正确率；首文本可能是中间说明，不一定是最终答案内容。指标必须说明口径。

### 8.3 适合面试准备的最小实验

准备一份固定、人工标注的测试集，先从几十条开始；以下为建议，非当前已经完成的报告。

- Runtime / 工具：正常调用、多工具、参数错误、取消、重复、确认恢复、配置变化、执行未知。
- 记忆：该写/不该写、否定、第三人称引用、数字、纠错、过期、忘记和两个用户隔离。
- RAG：精确实体、同义词、缩写、多轮指代、未覆盖知识、混淆文档、多跳与图片信息。

RAG 对比建议固定模型、数据、chunk、Top-K 与评测集，逐步比较：

```text
A：向量检索基线
B：A + 关键词融合
C：B + 重排
D：C + MMR
E：选定方案 + 查询改写（单独比较收益与额外消耗）
```

每次只改变一个主要因素，报告样本数、运行配置、错误案例和延迟/成本；样本小或模型随机性强时要报告波动，不应给出夸大的提升结论。

### 8.4 Trace 应该帮助回答的问题

- 请求走了哪种执行策略，为什么降级？
- 模型看到哪些工具、记忆和历史？哪些内容被省略？
- 检索候选从哪一路进入，经过哪些排序和过滤？
- 工具是否真的执行，还是因预算/确认/依赖被跳过？
- 最终答案引用了哪些证据，报告有哪些局限？
- 耗时和费用集中在哪些阶段？

Trace 会接触敏感输入与结果，应脱敏、限权限并设置保留策略；记录原文越多不代表观测越好。实际记录粒度应从当前 schema/实现核对。

### 9.3 有数据后如何改写

模板：

> 在 [样本数] 条固定测试集上，相比 [基线]，[方案] 的 [指标] 从 [A] 变为 [B]；p95 延迟变化为 [数值]，平均成本变化为 [数值]，主要改善 [错误类别]。

方括号是待填内容，不应把模板作为成果投递。只展示成功截图，没有基线和失败统计，无法证明优化收益。

### 9.4 AI 辅助开发如何回答

> 我使用 AI 辅助生成和修改代码，但模块职责、权限与状态约束由我定义。我通过源码审查、针对性测试和实际执行确认结果，发现问题后会追到协议或存储层。我能现场解释并修改核心链路，也会明确哪些路径目前只经过 mock 验证。

只在真实符合时使用这段话。面试官很可能要求现场改工具、调整压缩策略或排查一条 Trace，因此不要依赖背诵。

## 10. 演示与备考计划

### 10.1 十分钟演示

| 时间 | 演示 | 说明重点 |
|---|---|---|
| 0–1 分钟 | 项目目标与模块关系 | 聚焦四个核心模块 |
| 1–3 分钟 | 简单工具任务及取消 | 模型建议、服务端执行、UI 事件 |
| 3–5 分钟 | 私有笔记问答 | 检索与引用，打开 Trace 看候选 |
| 5–7 分钟 | 偏好记忆与纠错 | 原文依据、召回、版本语义 |
| 7–9 分钟 | 确认与恢复 | 使用当前明确需要确认的工具，避免真实高影响副作用 |
| 9–10 分钟 | 指标与边界 | 展示真实报告，承认尚未验证的部分 |

准备事先验证过的固定材料，不依赖现场上传大文件或随机外部服务。为模型慢响应准备已有 Trace，演示前确认凭据与敏感信息不会暴露。

### 10.2 七天备考

1. 第一天：画总链路，练习 30 秒与两分钟介绍，区分消息、快照、记忆和知识。
2. 第二天：读 Runtime 的预算、压缩、终态与策略降级，用测试验证工具配对。
3. 第三天：读工具契约、Router、并发与确认恢复，新增或修改一个低风险工具练手。
4. 第四天：读记忆召回、抽取校验、原子 writer 和 SQL，准备纠错/并发/忘记案例。
5. 第五天：读 RAG 各阶段，对固定问题查看真实候选、最终上下文与失败原因。
6. 第六天：运行最小 live eval 和消融，整理指标、局限与两条真实 Trace。
7. 第七天：按目标岗位模拟面试，练习“当前实现 → 取舍 → 证据 → 边界”的回答结构。

- 能否不用术语堆叠，讲清一条请求从页面到数据库的流程？

- 能否指出参数校验、资源授权与确认分别在哪里发生？
- 能否解释当前并发调度的执行顺序限制？
- 能否解释记忆事务与版本冲突分别解决什么？
- 能否拿出至少一组真实检索结果及失败样本？
- 能否指出词面引用检查无法识别的反例？
- 能否明确区分已实现、mock 已测、真实环境已验收和下一步设计？
